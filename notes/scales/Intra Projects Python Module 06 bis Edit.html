    Introduction
    

    
- Remain polite, courteous, respectful, and constructive
    throughout the evaluation process. The well-being of the community
    depends on it.

    - Together with the person (or group) being evaluated, identify any issues in the work.
    Take the time to discuss and debate the problems you have identified.

    - You must consider that there might be differences in how your
    peers have understood the project's instructions and the
    scope of its functionality. Always keep an open mind and grade
    their work as honestly as possible. The pedagogy is valid
    only if peer evaluation is conducted seriously.
    

    

    

    

    Guidelines
    

    
- Only grade the work that is in the student's or group's
    Git repository.

    - Double-check that the Git repository belongs to the student
    or the group. Ensure that the work is for the relevant project
    and also check that the "git clone" command is run in an empty folder.

    - Check carefully that no malicious aliases were used to fool you
    and make you evaluate something other than the content of the
    official repository.

    - To avoid any surprises, carefully check that both the evaluating
    and the evaluated students have reviewed any scripts that may be used
    to facilitate grading.

    - If the evaluating student has not completed that particular
    project yet, it is mandatory for this student to read the
    entire subject document prior to starting the defense.

    - Use the flags available on this scale to signal an empty repository,
    a non-functioning program, a norm error, cheating, etc. In these cases,
    the grading is over and the final grade is 0 (or -42 in the case of
    cheating). However, with the exception of cheating, you are
    encouraged to continue to discuss your work (even if you have not
    finished it) in order to identify any issues that may have caused
    this failure and to avoid repeating the same mistakes in the future.

    - Remember that for the duration of the defense, no unexpected,
    premature, uncontrolled termination of the program is allowed;
    otherwise, the final grade is 0. Use the appropriate flag. 
    You should never have to edit any file other than the configuration file, if one exists.
    If you want to edit a file, take the time to discuss the reasons with the 
    evaluated student and make sure both of you agree with this change.

    Exercises
    

    

    

    Exercise 0 - Data Processor
    

    

    If needed, ask the assessed person to help you with the tests.
    
Does the program correctly implement ALL the following features?
    


      

    • A file named data_processor.py exists
      • 

    • The program imports the abc module for abstract base classes, or specific elements from it (such as ABC)
      • 

    • DataProcessor is an abstract base class (inherits from ABC)
      • 

    • DataProcessor has @abstractmethod decorators on the validate() and ingest() methods
      • 

    • Method signatures match requirements:


        

      • validate(self, data: Any) -> bool
        • 

      • ingest(self, data: Any) -> None
        • 

      • output(self) -> tuple[int, str]
        • 

      • 

    • The NumericProcessor(), TextProcessor(), and LogProcessor() classes inherit from DataProcessor
      • 

    • All subclasses properly override the abstract methods with specialized behavior
      • 

    • NumericProcessor correctly validates and ingests numeric data (int, float, and lists of both types)
      • 

    • TextProcessor correctly validates and ingests string data (str and list of str)
      • 

    • LogProcessor correctly validates and ingests log data as a dict of strings (one per log entry) and a list of dict (multiple log entries)
      • 

    • Run python3 data_processor.py and verify that multiple tests cover the expected behaviours:
the validate() functions can detect valid and invalid data for each specialised class,
the data is correctly ingested and transformed into strings, and each call to output() on a data processor
returns the oldest element and removes it.
      • 

    • The program tests an ingest() with invalid data, and it raises an error correctly caught (this implies a mypy error)
      • 

    • Ask the assessed person to explain why abstract base classes are useful
      • 

    


    

    

    

    

    





    

    

    Exercise 1 - Polymorphic Processing of a Data Stream
    

    

    If needed, ask the assessed person to help you with the tests.
    
Does the program correctly implement ALL the following features?
    


      

    • A file named data_stream.py exists
      • 

    • The program is an improvement on the previous exercise, and all previously verified behaviours are still present
      • 

    • DataStream is a new class that implements register_processor() and process_stream()
      • 

    • Method signatures match the following requirements:


        

      • register_processor(self, proc: DataProcessor) -> None
        • 

      • process_stream(self, stream: list[typing.Any]) -> None
        • 

      • print_processors_stats(self) -> None
        • 

      • 

    • The process_stream() method calls the validate() and ingest() methods from all registered data processor using polymorphic calls
      • 

    • The program correctly handles invalid data in the stream
      • 

    • The statistics are displayed for all registered data processors, either by accessing attributes directly or using an extra method
      
from each data processor
      • 

    • Ask the assessed person to explain how polymorphism enables the DataProcessor class to handle different data types in a stream
      • 

    


    

    

    

    

    





    

    

    Exercise 2 - Data Pipeline
    

    

    If needed, ask the assessed person to help you with the tests.
    
Does the program correctly implement ALL the following features?
    


      

    • A file named data_pipeline.py exists
      • 

    • The program is based on the previous exercise and extends it
      • 

    • The new class ExportPlugin is created and inherits from Protocol
      • 

    • The ExportPlugin class defines a method with the following signature:
process_output(self, data: list[tuple[int, str]]) -> None
      • 

    • At least two independent classes (CSV and JSON) exist and conform to the ExportPlugin constraints
      • 

    • The DataStream class has a new method that exports the processed data from the stream to a plugin:
      
output_pipeline(self, nb: int, plugin: ExportPlugin) -> None
      • 

    • Ask the learner to explain the difference between Protocol (duck typing) and ABC (abstract base class),
      
and why a plugin system wants the former
      • 

    


    

    

    

    

    





    

    

    Exercise 3 - Entity Factories and Capabilities
    

    

    Note: the subject suggests entity and factory names. The evaluated project can use different names
    
as long as the design patterns are correctly implemented. This note is valid throughout the defense.
    


    Check the content of the ex3/ folder:
    


      

    • it contains an init.py file and at least one other file, but multiple files are allowed.
      • 

    • the code defines the Creature abstract class, inheriting from ABC. attack() is an abstract method
and describe() is a concrete method.
      • 

    • at least two plain concrete classes inherit from Creature (for example Flameling and Pyrodon).
      • 

    • the code defines the CreatureFactory abstract class, inheriting from ABC, with the create_base()
and create_evolved() abstract methods.
      • 

    • at least two concrete factory classes exist, each producing a base and an evolved entity (a family).
      • 

    • the code defines the TransformCapability abstract class, inheriting from ABC, with the transform()
and revert() abstract methods. Other capabilities are allowed.
      • 

    • the capability class does NOT inherit from Creature. This is the point of the exercise.
      • 

    • at least two concrete classes inherit from Creature plus the capability class (for example
Shiftling and Morphagon), and their state changes what attack() returns.
      • 

    • the init.py file must only expose the factories, never the concrete entities.
      • 

    


    Check that the script "battle.py" is present and follows the scenario:
    


      

    • it instantiates both factories.
      • 

    • a single function accepts any factory and, for it, creates the base entity, describes it and
attacks, then repeats with the evolved entity; it works with both factories.
      • 

    • another function receives two factories, creates one entity from each, presents them and makes
them fight.
      • 

    


    Check that the script "capacitor.py" is present and follows the scenario:
    


      

    • it creates the transform factory and, for the base then the evolved entity, uses describe() and
attack() plus the capability (transform, attack again, revert) at the right place.
      • 

    


    Ask the learner what would break if transform() and revert() had been placed on the Creature base
    
class instead.
    


    If everything works, and the abstract factory pattern and the separate capability are correctly
    
implemented, tick "Yes". Otherwise, tick "No".
    


    

    

    

    

    





    

    

    Exercise 4 - Abstract Strategy
    

    

    Check the content of the ex4/ folder:
    


      

    • it contains an init.py file and at least one other file, but multiple files are allowed.
      • 

    • the code defines the BattleStrategy abstract class, inheriting from ABC, with abstract act() and
is_valid() methods.
      • 

    • at least two concrete strategy classes inherit from BattleStrategy.
      • 

    • a "normal" strategy exists and is suitable for any entity, whatever the family or the capability.
      • 

    • a capability-aware strategy exists and matches a capability from ex3 (for example an aggressive
strategy that works with a TransformCapability entity: transform, attack, then revert).
      • 

    


    Check that the script "tournament.py" is present and follows the scenario:
    


      

    • it instantiates entity factory classes from ex3 and the strategies.
      • 

    • a single battle() function handles the tournament (you can create sub-functions).
      • 

    • battle() accepts a list of tuples, each consisting of a CreatureFactory and a BattleStrategy.
      • 

    • it makes each pair of opponents fight once (an entity does not fight itself, and A-B is not
repeated as B-A).
      • 

    • each entity's associated strategy is applied during the fight (a transforming entity transforms
with the aggressive strategy, but not with the normal one).
      • 

    • an unsuitable strategy for an entity stops the tournament.
      • 

    


    Ask the learner where the per-family decision moved to, given that the tournament code never checks
    
which family an entity belongs to.
    


    If everything works, and the abstract strategy pattern is correctly implemented, tick "Yes".
    
Otherwise, tick "No".
    


    

    

    

    

    





    

    

    

    

    

    

    Code Quality and Understanding
    

    

    

    Code Quality and Understanding
    

    

    Evaluate the overall code quality and learner understanding:
    


      

    • Is the code written in Python 3.10 or higher?
      • 

    • Does the code adhere to the flake8 linter standards (no errors)?
      • 

    • Comprehensive type annotations are used throughout (all functions and methods have
parameter and return types). Check this using mypy (note that there is an intentional
exception on Exercise 0).
      • 

    • Docstrings are NOT required for this module.
      • 

    • eval() and exec() are not used anywhere, and no external library is imported.
      • 

    • Proper use of ABC and @abstractmethod decorators for abstract base classes
      • 

    • Proper use of Protocol for the export plugins
      • 

    • Error handling is implemented appropriately
      • 

    • Is the code well-structured and readable?
      • 

    


    Understanding:
    


      

    • The learner can explain what abstract base classes are and why they are useful
      • 

    • The learner understands when and why to use polymorphism, and can demonstrate how the
same interface works with different implementations
      • 

    • The learner understands that @abstractmethod forces subclasses to implement specific methods
      • 

    • The learner can explain each design pattern used (abstract factory,
capabilities, abstract strategy) and what problem it solves
      • 

    


    Answer "Yes" if all quality standards are met, and "No" if any are lacking.
