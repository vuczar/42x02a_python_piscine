    Introduction
    

    
- Remain polite, courteous, respectful, and constructive
    throughout the evaluation process. The well-being of the community
    depends on it.

    - Together with the person (or group) being evaluated, identify any issues in the work.
    Take the time to discuss and debate the problems you have identified.

    - You must consider that there might be differences in how your
    peers have understood the project's instructions and the
    scope of its functionality. Always keep an open mind and grade
    their work as honestly as possible. The pedagogy is valid
    only if peer evaluation is conducted seriously.
    

    

    

    

    Guidelines
    

    
- Only grade the work that is in the student's or group's
    Git repository.

    - Double-check that the Git repository belongs to the student
    or the group. Ensure that the work is for the relevant project
    and also check that the "git clone" command is run in an empty folder.

    - Check carefully that no malicious aliases were used to fool you
    and make you evaluate something other than the content of the
    official repository.

    - To avoid any surprises, carefully check that both the evaluating
    and the evaluated students have reviewed any scripts that may be used
    to facilitate grading.

    - If the evaluating student has not completed that particular
    project yet, it is mandatory for this student to read the
    entire subject document prior to starting the defense.

    - Use the flags available on this scale to signal an empty repository,
    a non-functioning program, a norm error, cheating, etc. In these cases,
    the grading is over and the final grade is 0 (or -42 in the case of
    cheating). However, with the exception of cheating, you are
    encouraged to continue to discuss your work (even if you have not
    finished it) in order to identify any issues that may have caused
    this failure and to avoid repeating the same mistakes in the future.

    - Remember that for the duration of the defense, no unexpected,
    premature, uncontrolled termination of the program is allowed;
    otherwise, the final grade is 0. Use the appropriate flag. 
    You should never have to edit any file other than the configuration file, if one exists.
    If you want to edit a file, take the time to discuss the reasons with the 
    evaluated student and make sure both of you agree with this change.

    Preliminaries
    

    

    

    Basics
    

    

      

    • Only grade the work that is in the learner's Git repository.
      • 

    • Ensure the Git repository belongs to the learner.
      • 

    • Check that no malicious aliases are used.
      • 

    • Verify that the project structure matches the subject requirements and the file tree:
the ex0/ and ex1/ folders exist, and the alchemy package and the ft_*.py scripts are at
the root of the repository.
      • 

    • Ensure that no virtual environment and no .env file containing real secrets is committed.
      • 

    


    Are all preliminary checks satisfied?
    


    

    

    

    

    





    

    

    

    

    

    

    Exercises
    

    

    

    Exercise 0 - The Sealed Laboratory
    

    

    Navigate to the ex0/ folder. Required files: construct.py, loading.py,
    
requirements.txt, pyproject.toml
    


    Part 1, sealing the room. Test construct.py:
    


      

    1. Run it outside a virtual environment.
      2. 

    2. Create a virtual environment as instructed by the program.
      3. 

    3. Activate it and run the program again.
      4. 

    


    The program should:
    


      

    • Correctly detect whether it is running inside a virtual environment
      • 

    • Display a clearly different output in each scenario
      • 

    • Provide clear instructions for creating a virtual environment
      • 

    • Show the relevant path information, including where packages get installed
      • 

    


    Part 2, stocking the reagents. Test the dependency management:
    


      

    1. Try running loading.py without the dependencies installed.
      2. 

    2. Install them with pip (requirements.txt) and run it again.
      3. 

    3. If Poetry is available, test the Poetry installation (pyproject.toml).
      4. 

    


    The program should:
    


      

    • Handle a missing dependency gracefully, with a helpful message that gives the install
command for both pip and Poetry, and never crash
      • 

    • Import the declared dependencies and report the installed version of each
      • 

    • Show the difference between pip and Poetry through its output
      • 

    


    Check the dependency files:
    


      

    • requirements.txt: are the required packages listed with appropriate versions?
      • 

    • pyproject.toml: is it properly formatted for Poetry?
      • 

    


    Ask the learner to explain:
    


      

    • What a virtual environment is, what it isolates and what it does not
      • 

    • How their program detects it
      • 

    • The difference between pip and Poetry, and why dependency management matters
      • 

    


    Does the exercise work correctly and does the learner demonstrate understanding?
    


    

    

    

    

    





    

    

    Exercise 1 - The Oracle
    

    

    Navigate to the ex1/ folder. Required files: oracle.py, requirements.txt,
    
.env.example, .gitignore
    


    Before testing, ask the reviewee to:
    


      

    1. Show that python-dotenv is declared in their requirements.txt
(they may carry one over from ex0/).
      2. 

    2. Create and activate a virtual environment, then install the dependencies:
      


      $> python3 -m venv .venv
      
$> source .venv/bin/activate
      
$> pip install -r ex1/requirements.txt
      3. 

    


    The reviewee must perform these steps themselves. Do not install anything
    
manually as a reviewer.
    


    Then test the configuration:
    


      

    1. Run oracle.py with no environment variable set.
      2. 

    2. Create a .env file from .env.example with test values, and run it again.
      3. 

    3. Run it once more with a variable set directly in the shell, and check that the
shell value wins over the .env file.
      4. 

    


    The program should:
    


      

    • Use the python-dotenv library to load the .env file
      • 

    • Load its configuration from environment variables
      • 

    • Behave visibly differently in development and in production
      • 

    • Handle missing configuration without crashing
      • 

    • Show the loaded configuration without exposing real secrets
      • 

    


    Check the security implementation:
    


      

    • .env.example contains template values, not real secrets
      • 

    • .gitignore excludes the .env file
      • 

    • oracle.py contains no hardcoded secret
      • 

    


    Ask the learner to explain:
    


      

    • Why an environment variable is a better place for a secret than a constant in the code
      • 

    • What is still not safe about an environment variable
      • 

    • Why secrets must never be committed to version control
      • 

    • How python-dotenv fits in
      • 

    


    Does the exercise work correctly and does the learner demonstrate understanding?
    


    

    

    

    

    





    

    

    Exercise 2 - The Alembic
    

    

    Test the Alembic scripts, at the root of the repository:
    


      

    • Run: python3 ft_alembic_[0-1].py
      • 

    • The output of each script should demonstrate the same elements as in the example.
      • 

    • ft_alembic_0 uses "import elements" and calls "elements.create_fire()"
      • 

    • ft_alembic_1 uses "import alchemy" and calls "alchemy.create_air()". It then tries
to reach "alchemy.create_earth()" through the package interface, and this must fail
(uncaught exception allowed, mypy error expected).
      • 

    • Check that elements.py at the root defines create_fire() and create_water(), and that
alchemy/elements.py defines create_earth() and create_air().
      • 

    • Verify that the alchemy package has an init.py file which exposes "create_air"
from ".elements" (alternative solutions exist and are accepted) but NOT "create_earth".
Other elements of this file are checked in the following questions.
      • 

    • Check that sys.path is not modified anywhere.
      • 

    


    Ask the learner why alchemy/elements.py defines create_earth yet ft_alembic_1 cannot
    
reach it through "import alchemy", given that nothing was made private.
    


    

    

    

    

    





    

    

    Exercise 3 - Distillation and Transmutation
    

    

    Distillation. Run: python3 ft_distillation_0.py
    


      

    • Verify that direct access to the alchemy/potions.py file is used and works in
distillation_0, testing both the strength and the healing potion.
      • 

    • Check that potions.py correctly imports both the root elements.py and
alchemy/elements.py. Note that one of them is outside the package.
      • 

    


    Transmutation. Run: python3 ft_transmutation_0.py
    


      

    • Verify access to the "lead_to_gold" recipe using the
alchemy/transmutation/recipes.py file directly (transmutation_0).
      • 

    • Check that the transmutation subpackage has an init.py file.
      • 

    • Check that recipes.py contains at least one absolute import AND one relative import.
      • 

    


    Ask the learner when to use an absolute pathway and when to use a relative one, and
    
confirm they understand the difference between the import methods used so far.
    


    

    

    

    

    





    

    

    Exercise 4 - Avoid the Explosion
    

    

    Test the circular dependency experiment:
    


      

    • Run: python3 ft_kaboom_[0-1].py
      • 

    • Verify that ft_kaboom_0 records a light spell flawlessly, and that ft_kaboom_1 fails
on an import error (uncaught exception allowed).
      • 

    • Check that alchemy/grimoire/ contains the expected files: the light_* and dark_*
Python files, and an init.py file.
      • 

    • Check that the allowed ingredients are defined in the spellbook and NOT in the
validator, and that both files genuinely need each other. If the mutual dependency
is not there, the exercise is void.
      • 

    • Check that "Earth, wind and fire" records the spell "Fantasy" as VALID.
      • 

    • Check that the dark pair fails because of the import cycle itself, and not because
of some other error.
      • 

    • Verify that the circular dependency problem is explained.
      • 

    • Ask the learner which solution they used to avoid it in the light grimoire, and what
the other options were.
      • 

    


    Both grimoires describe two files that need each other, and only one explodes. The
    
learner must be able to explain why.
    


    

    

    

    

    





    

    

    

    

    

    

    Code Quality and Understanding
    

    

    

    Code Quality and Understanding
    

    

    Evaluate the overall code quality:
    


      

    • Is the code written in Python 3.10 or higher?
      • 

    • Does the code adhere to the flake8 linter standards (no errors)?
      • 

    • Comprehensive type annotations are used throughout (all functions have parameter and
return types). Check this using mypy. Note the intentional exception: the
hidden-symbol call in ft_alembic_1.py.
      • 

    • Docstrings are NOT required for this module.
      • 

    • eval() and exec() are not used anywhere.
      • 

    • sys.path is not modified anywhere.
      • 

    • Is the overall code organization clean and professional?
      • 

    


    Understanding. Ask the learner to explain how the two halves of this project fit
    
together: how a virtual environment, declared dependencies, environment-based
    
configuration and a well-organised package would be set up together at the start of a
    
real project, and what goes wrong without each of them.
    


    Is the overall code quality satisfactory?
